# Helper process resource

`io-host.start-helper` is the sole canonical helper execution primitive. It starts a host-approved helper and returns an invocation-scoped `helper-process`; a failure to start is returned as `helper-error`. The caller obtains output only through `next-event`, which waits until an event is available or the process reaches terminal EOF. Output events carry non-empty arbitrary byte chunks and identify stdout or stderr. Chunks are not lines: bytes, including carriage returns and invalid text encodings, are preserved unchanged. Event order is the host-observed order of delivery and does not assert an unknowable total ordering of simultaneous writes to separate OS streams.

The host MUST begin draining stdout and stderr independently of calls to `next-event`. It MUST preserve all bytes accepted from either stream, including during cancellation, timeout, process/runtime failure, or child crash. Bounded in-memory queues alone are insufficient unless backpressure cannot block the child; implementations MUST use bounded buffering and/or spooling such that slow event consumption cannot fill child pipes or silently discard output. For each output event, the complete encoded `next-event` response MUST fit the plugin-advertised receive-frame maximum. Large logical output writes are split into as many ordered events as needed; no smaller hidden helper-output chunk ceiling applies, and splitting preserves every byte and per-stream order. If the host cannot retain or deliver output, it reports a host/runtime terminal failure after exposing all output it did accept.

Exactly one terminal event follows all accepted output: `exited({code, output})` for any normal process exit, including non-zero codes; `cancelled` when canonical cancellation was accepted; `timed-out` when the host timeout policy fires; or `failed(detail)` for other host/runtime failures. Platform signal details are not portable status. No output event follows terminal. After terminal is consumed, subsequent `next-event` returns `none`. Output draining and EOF resolution precede terminal delivery. Cancellation is idempotent and follows a linearizable first-terminal-condition-wins rule: if terminal has already been determined, later cancellation is a no-op; otherwise accepted cancellation requests termination and determines `cancelled`, unless another terminal condition already won. The host remains responsible for draining pending output, reaping the child, and cleanup. Dropping the resource or ending its invocation MUST terminate and reap any still-running child and invalidate its streams; dropping MUST NOT orphan it.

The `output` member of a normal `exited` payload is the optional owned staged writer transferred back to the plugin, if it remained valid. On cancellation, timeout, runtime/helper/staging failure, process drop, or invocation cleanup, the host discards the writer and never returns it. A writer write failure poisons that writer and determines host/runtime failure. If `start-helper` fails after its request is accepted, ownership of transferred input/output resources remains consumed; the host cleans them up.

`start-helper` transfers an optional staged writer as an owned resource. The host and live process own it while the helper runs; the plugin cannot use it during that lifetime. On normal exit, the writer is returned in the `exited` terminal payload for the plugin to `finish()`, if valid. On cancellation, timeout, host/runtime failure, staging-write failure, drop, or invocation cleanup, it is discarded and not returned. Transferred input and output remain consumed if start fails after the request frame is accepted.

Without an output writer, stdout and stderr are both delivered as live byte events and `stdout-activity` MUST NOT appear. With an output writer, stdout payload bytes go directly to the writer and MUST NOT appear as `output(stdout, ...)`; instead the host emits cumulative `stdout-activity` byte-count events. Counts MUST be monotonic and catch up before terminal to all stdout bytes successfully accepted by the writer; activity events may be coalesced. Stderr remains fully delivered as live byte events in either mode. The writer path MUST preserve all stdout bytes; a write failure poisons the writer and results in host/runtime failure after pending stderr and accepted events are delivered. Input continues to be streamed to stdin using the transferred invocation-scoped byte-stream. Credentials remain host-mediated, and helper execution does not expose filesystem or Vault paths. A silent running process is not meaningful liveness solely because it exists; stdout activity, output, and other genuinely host-observed work may be.

These rules let a synchronous convenience wrapper be implemented by consuming the same event stream; no separate buffered execution path is part of the contract. The contract does not define provider-output parsing or expand generic progress.
