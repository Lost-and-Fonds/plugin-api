# Helper process resource

`io-host.start-helper` is the sole canonical helper execution primitive. It starts a host-approved helper and returns an invocation-scoped `helper-process`; a failure to start is returned as `helper-error`. The caller obtains output only through `next-event`, which waits until an event is available or the process reaches terminal EOF. Output events carry non-empty arbitrary byte chunks and identify stdout or stderr. Chunks are not lines: bytes, including carriage returns and invalid text encodings, are preserved unchanged. Event order is the host-observed order of delivery and does not assert an unknowable total ordering of simultaneous writes to separate OS streams.

The host MUST begin draining stdout and stderr independently of calls to `next-event`. It MUST preserve all bytes accepted from either stream, including during cancellation, timeout, process/runtime failure, or child crash. Bounded in-memory queues alone are insufficient unless backpressure cannot block the child; implementations MUST use bounded buffering and/or spooling such that slow event consumption cannot fill child pipes or silently discard output. If the host cannot retain or deliver output, it reports a host/runtime terminal failure after exposing all output it did accept.

Exactly one terminal event follows all accepted output: `exited(code)` for any normal process exit, including non-zero codes; `cancelled` when canonical cancellation was requested; `timed-out` when the host timeout policy fires; or `failed(detail)` for other host/runtime failures. Platform signal details are not portable status. No output event follows terminal. After terminal is consumed, subsequent `next-event` returns `none`. Output draining and EOF resolution precede terminal delivery. Cancellation is idempotent and requests termination; the host remains responsible for draining pending output, reaping the child, and cleanup. Dropping the resource or ending its invocation MUST terminate and reap any still-running child and invalidate its streams; dropping MUST NOT orphan it.

Without an `output` staged-writer, stdout and stderr are both delivered as live byte events. With an `output` writer, stdout payload bytes are drained directly into the writer and MUST NOT be duplicated in the process event stream; instead the host emits `stdout-activity(total-bytes)` events with cumulative host-observed stdout byte counts. These activity events MUST be emitted as output is accepted, not deferred until process exit. They report activity and byte volume without transporting payload a second time. Stderr remains fully delivered as live byte events regardless of the writer, so diagnostics are not suppressed. The writer path MUST preserve all stdout bytes; if writing fails, it becomes unfinalizable under the staging rules and the process eventually reports host/runtime failure after pending stderr and accepted output events are delivered. The caller finalizes the writer only after successful terminal completion. Input continues to be streamed to stdin using the transferred invocation-scoped byte-stream. Credentials remain host-mediated, and helper execution does not expose filesystem or Vault paths. A silent running process is not meaningful liveness solely because it exists; stdout-activity, stderr/stdout output, and other genuinely host-observed work may be.

These rules let a synchronous convenience wrapper be implemented by consuming the same event stream; no separate buffered execution path is part of the contract. The contract does not define provider-output parsing or expand generic progress.
