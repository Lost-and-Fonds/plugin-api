# Plugin package metadata

This document normatively defines package manifest discovery, loading, identity, and component metadata. The generated [`plugin-package.schema.json`](../schema/plugin-package.schema.json) validates the manifest shape. Each package has one stable `id`, a `version`, a required `contract` containing the exact canonical Stashd WIT package identity (for example, `stashd:plugin@0.18.0`), and a `components` object keyed by stable component IDs.

## Package loading boundary

The contract begins when an implementation has obtained one unpacked package root representing an immutable package snapshot. How the root is obtained is implementation-specific and outside this contract. A conforming package MUST contain its sole authoritative manifest at `<package-root>/stashd-plugin.json`. A host MUST read that exact path; it MUST NOT search directories, try alternate filenames, or rely on SDK conventions, host conventions, package-manager metadata, installation paths, or external files. A manifest elsewhere does not satisfy a missing canonical manifest. Package managers MAY cache or index manifest data, but package contents remain the normative source.

The manifest is UTF-8 encoded JSON. Its top-level JSON value MUST be the plugin package manifest object. A host reads and parses those bytes, rejecting duplicate JSON object member names at any nesting depth during parsing. Duplicate means the exact same member name as represented by the parser's JSON string model; hosts MUST NOT normalize names or compare them case-insensitively. A host MUST reject a duplicate-member manifest before schema validation, contract compatibility evaluation, artifact resolution, process launch, RPC startup, or lifecycle execution. It then validates the resulting object against the canonical package schema and semantic rules in this repository and evaluates its package-level `contract` identity. Missing or unreadable canonical manifest, malformed JSON, duplicate object members, schema-invalid input, semantic validation failure, and unsupported contract identity are package-loading failures. This manifest parsing rule is distinct from RPC v1 frame parsing; it does not define RPC duplicate-member behavior.

A host MUST complete package loading in this order before launching a component process or sending lifecycle RPC: (1) obtain the immutable unpacked package root; (2) read the manifest from the canonical path; (3) parse UTF-8 JSON; (4) validate schema and package semantic rules; (5) determine whether the exact `contract` identity is supported and reject unsupported identities; (6) resolve every declared component artifact against this same package root under [package artifact resolution](package-artifact.md), including its normalization, symlink, containment, and regular-file rules; and (7) complete required package/component structural validation. Any failure in these steps prevents lifecycle execution. Component launch, RPC startup, and lifecycle invocation may begin only after all loading steps succeed. No semver compatibility is implied, and RPC `hello` version negotiation remains separate from WIT contract compatibility. The `contract` applies to every component governed by the manifest and identifies the exact WIT contract each implements; it is independent of the plugin package's own `version`. Every valid package declares exactly one such identity. The schema constrains it to this repository's current canonical identity. Static schema validation establishes well-formed identity, not whether a particular host supports it. Each component selects a canonical WIT `world`, a package-relative logical `artifact`, and optionally declares credential slots. The `artifact` identifies the component program; package-artifact resolution determines the contained regular file, and [component execution](component-execution.md) defines how it is launched. The `world` specifies which canonical WIT world the component implements. Multiple components MAY refer to the same artifact when one executable implements multiple worlds/components. Components of different worlds sharing an executable are distinguishable through their canonical lifecycle methods. Components with the same WIT world that share an artifact MUST NOT require knowledge of the selected component ID for correctness: any required distinction MUST be represented through canonical lifecycle inputs, configuration, or credential bindings, or the package MUST use distinct component launcher artifacts. Same-world aliases MUST NOT rely on hidden component-selection state. Core retains the selected component identity for host configuration, credential-slot identity, UI, persistence, and related host responsibilities; no component ID is added as a universal lifecycle field. Artifact path normalization, resolution, and containment are defined separately in [Package artifact resolution](package-artifact.md). RPC `hello` negotiates only the RPC protocol version and MUST NOT be treated as identifying or repairing the package's missing or unsupported WIT contract identity. RPC protocol version determines message transport/encoding; `contract` determines the WIT API shape. Support for one does not imply support for the other.

## Component credential slots

Each component may declare `credential_slots`, an object keyed by stable slot names. An omitted or empty object means the component declares no credential requirements. Names use the component-ID syntax `^[a-z0-9][a-z0-9._-]*$`; names are unique by construction within the component. Slot identity is the tuple `(package id, component id, slot name)`. The same name in distinct components is independent and never implies shared configuration.

A slot descriptor requires `label` and `required`, and may include `description`. These strings are presentation metadata only and do not participate in identity. Declarations contain no credential reference, secret, credential taxonomy, provider, scopes, or protocol placement.

The package declares requirements; Core/configuration persists the user's choice of stored credential reference per slot; invocation bindings grant temporary use. A `credential-reference` is an opaque host selector, not a secret or authorization. A `credential-binding` maps the declared slot name to that reference and is supplied only when Core authorizes it for the invocation. Bindings MUST correspond to slots declared by that component; plugins MUST NOT rely on hidden or undeclared names.

`required: true` means the component cannot perform its normal configured function without a binding. `required: false` means it may work anonymously or with reduced functionality. Neither value grants permission or guarantees validity or availability. Hosts may defer invocation when a required binding is absent; every use still undergoes invocation authorization and use-time availability/revocation checks, preserving `credential-denied` versus `credential-unavailable`.

Keep a slot name when the logical requirement remains the same. Rotating/replacing the stored credential reference or changing presentation text preserves identity. Adding an optional slot is configuration-compatible; adding a required slot can leave existing installations incompletely configured. Renaming or removing a slot changes the configuration contract and MUST NOT silently transfer its binding. Hosts MUST NOT infer equivalence between differently named slots; no migration framework is implied.

For example, `input.account` and `broadcast.account` in one package are separate slots. Core may let a user select the same stored reference for both, but that is an explicit host/user decision. A website Input declaring `session` may bind a refreshed session reference without changing that slot identity. The Input invocation receives only explicitly granted bindings. HTTP and helper capabilities mediate credential use; the existing Input-only `input-host.open-credential(reference)` remains available only for protocols those capabilities cannot express. Browsertrix/Chromium/Playwright helpers receive only the invocation's explicit bindings; generic helper mediation carries opaque session material without browser-specific WIT. Broadcast and Enrichment do not gain raw-secret access.

This covers API-backed private YouTube and Internet Archive Input, Internet Archive/Broadcast and Jellyfin/Plex destinations, S3/WebDAV Broadcast, helper-backed SFTP, authenticated Enrichment APIs, and multiple independent slots on one component. Each declares only its own stable names, Core stores references by component-scoped identity, and invocation bindings carry name/reference pairs. Use host-mediated HTTP or helper execution where applicable; Input may use its existing raw-secret escape hatch only when mediation is insufficient. Optional slots permit anonymous operation. No package metadata contains secrets or references.
